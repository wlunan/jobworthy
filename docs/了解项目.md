# 校招雷达项目导读

本文记录项目当前真实结构、招聘数据来源和抓取链路，供二次开发时快速定位。内容以仓库现状为准；README 中部分版本号、文件结构和数据量已经落后。

## 1. 项目定位

校招雷达是一个“纯前端单页应用 + 静态 JSON 数据 + Python 同步脚本 + 可选本地代理”的招聘信息聚合项目。

项目没有传统业务后端和数据库，也没有 npm 构建流程。GitHub Pages 可以直接托管 `index.html` 和 `jobs.json`。

```text
公开腾讯文档 ── scripts/sync_tencent_docs.py ──> jobs.json ──┐
                                                       ├──> index.html
企业招聘页面 ── Firecrawl / AnySearch ────────────────┘
                              ▲
                              └── tools/proxy.js（可选本地代理）
```

## 2. 关键文件

| 文件 | 职责 | 备注 |
|---|---|---|
| `index.html` | GitHub Pages 入口和当前完整版应用 | HTML、CSS、JavaScript和站点配置集中在一个文件中 |
| `applications.html` | 个人投递工作台 | 使用 Tabulator 提供多维表格式编辑、筛选和导入导出 |
| `archive/xiaozhao-radar.html` | 旧版独立页面 | 页面版本约为 v2.0.2，仅供历史参考 |
| `jobs.json` | 页面优先加载的聚合招聘数据 | 由同步脚本生成，结构为 `{updated,count,jobs}` |
| `scripts/sync_tencent_docs.py` | 腾讯文档离线同步脚本 | 拉取、解析、清洗、过滤、去重并生成根目录 `jobs.json` |
| `tools/proxy.js` | 本地 CORS/请求转发代理 | 服务于 AnySearch 和腾讯文档浏览器兜底，默认端口 8787 |
| `archive/jobs-2026-08-11.json` | 历史数据备份 | 当前不被程序读取，也未纳入正式同步流程 |
| `docs/SYNC.md` | 腾讯文档同步说明 | 描述字段映射和发布流程 |
| `manifest.json` | 项目元数据 | `main` 指向正式入口 `index.html` |

README 描述了 `clis/xiaozhao/search.js` 和 `clis/xiaozhao/utils.js`，但当前仓库不存在 `clis` 目录。二次开发时不要假设 OpenCLI 适配器已经包含在仓库中。

## 3. 招聘数据来源

### 3.1 腾讯文档智能表格

当前 `jobs.json` 的主要来源是公开腾讯文档智能表格：

```text
https://docs.qq.com/smartsheet/DTkRMUVhoUWJXZEhJ
```

脚本配置的两个子表为：

| 子表 ID | 名称 |
|---|---|
| `tTNjGc` | 27届内推汇总 |
| `tvVDZj` | 实习提前批每日更新 |

`scripts/sync_tencent_docs.py` 使用腾讯文档的非公开 `dop-api/opendoc` 接口匿名读取表格。响应处理链路为：

```text
JSONP
  → clientVars.collab_client_vars.initialAttributedText.text[0].smartsheet
  → Base64 解码
  → zlib 解压
  → 腾讯智能表格内部 JSON
  → 中文字段记录
```

注意：这是腾讯内部接口和内部字段结构，不是稳定的公开 API。接口权限或 `k1`、`k2`、`k30`、`k31` 等结构变化后，同步脚本可能失效。

### 3.2 企业招聘网站和官方招聘页面

待抓取网址维护在 `index.html` 的 `CRAWL_SITES` 数组中。来源包括：

- 企业招聘官网；
- 校园招聘专题页面；
- 飞书招聘、Moka、智业等企业招聘系统；
- 企业官方微信公众号文章；
- 少量综合招聘网站。

每个站点配置大致为：

```javascript
{
  cat: "企业名称",
  url: "企业招聘页面地址",
  ind: "行业分类",
  t: "企业类型"
}
```

项目不是自动发现企业网址，而是按这份预设 URL 清单逐个抓取。

### 3.3 浏览器缓存

`index.html` 不再内置招聘数据快照。浏览器会使用 localStorage 缓存历史结果，在 `jobs.json` 暂时不可用时作为回退。

## 4. 企业页面使用什么工具抓取

### 4.1 Firecrawl：自动抓取主工具

浏览器调用 Firecrawl 云端 API，请求 `CRAWL_SITES` 中的企业网址。Firecrawl 将网页转换成 Markdown/文本，前端再用关键词和链接规则生成招聘记录。

```text
index.html → Firecrawl API → 企业招聘页面 → Markdown → 前端通用解析
```

实际网页请求由 Firecrawl 云端完成，不是用户浏览器直接爬取。API Key 的选择和存储逻辑位于 `index.html`。

### 4.2 AnySearch：自动备用工具

Firecrawl 失败后，页面尝试使用 AnySearch 提取网页内容。由于浏览器跨域限制，请求通常需要经过：

1. 本地 `tools/proxy.js`；或
2. 页面配置的公共 CORS 代理。

```text
index.html → tools/proxy.js/CORS 代理 → AnySearch API → 企业页面
```

### 4.3 BrowserAct：手动备用工具

遇到强反爬、验证码或复杂动态页面时，README 建议用户本地运行 BrowserAct：

```bash
browser-act stealth-extract "招聘页面URL" --out ba_result.json
```

生成 JSON 后通过页面导入功能载入。这不是页面自动执行的链路。

### 4.4 OpenCLI：文档中的手动备用方案

README 给出了类似命令：

```bash
opencli xiaozhao search "2027 校招" -f json > xiaozhao.json
```

但当前仓库缺少对应 `clis/xiaozhao` 适配器源码，因此仅凭当前仓库不能确认该命令可用。

## 5. 页面数据加载顺序

`index.html` 启动后主要按以下顺序获取可展示数据：

```text
jobs.json
  ↓ 加载失败
localStorage 历史缓存
```

Firecrawl/AnySearch 属于用户触发的企业网站抓取能力，不等同于页面默认加载的 `jobs.json` 数据。

投递管理使用独立的 localStorage 键 `xiaozhao_radar_applications_v2` 保存，包含岗位快照、渠道、状态、投递日期、一面日期、备注及记录时间。它不会写回公开数据，也不会因每日替换 `jobs.json` 而整体丢失。

招聘机会页使用 `xiaozhao_radar_view_state_v1` 保存搜索词、筛选条件、排序方式、页码和每页条数。页面再次打开时，先加载最新岗位数据，再恢复并应用该视图状态。

岗位与投递记录通过以下稳定键关联：

```text
公司 + 岗位 + 地点 + 投递链接
```

上述任一字段在数据源中发生变化时，会被识别为一个新岗位，旧的本地跟进记录仍保留但不会自动关联。

`applications.html` 支持 JSON 备份导入/导出和 CSV 表格导出。JSON 是完整恢复格式，CSV 主要用于 Excel/WPS 查看和分析。旧的 `xiaozhao_radar_tracking_v1` 会在投递工作台首次打开且新数据为空时尝试迁移。

## 5.1 自动部署与每日同步

`.github/workflows/pages.yml` 同时负责：

- `main` 分支更新后的 GitHub Pages 部署；
- 每天北京时间 09:30 运行 Python 同步脚本；
- `jobs.json` 有变化时自动提交；
- 上传静态站点并通过 GitHub Pages 发布。

首次启用需要在 GitHub 仓库 Settings → Pages 中选择 GitHub Actions 作为发布来源。

因此需要区分两类数量：

- `CRAWL_SITES` 数量：可尝试抓取的网站节点数量；
- `jobs.json.count`：腾讯文档同步后得到的招聘记录数量。

两者不能直接比较。

## 6. `jobs.json` 数据格式

顶层结构：

```json
{
  "updated": "YYYY-MM-DD",
  "count": 1603,
  "jobs": []
}
```

单条记录采用压缩键名：

| 键 | 含义 | 腾讯文档字段/生成方式 |
|---|---|---|
| `c` | 公司名称 | 公司名称 |
| `p` | 岗位标题 | 招聘岗位；为空时使用批次 |
| `ut` | 岗位更新时间 | 腾讯表格“更新日期” |
| `l` | 地点 | 从工作地点等文本识别城市 |
| `e` | 预留字段 | 当前固定为空字符串 |
| `w` | 批次 | 腾讯表格“批次” |
| `d` | 截止日期 | 招聘截止日期 |
| `s` | 来源 | 当前固定为“校招信息聚合平台” |
| `t` | 大类 | 互联网科技映射为“互联网”，其他映射为“其他” |
| `ind` | 行业 | 按关键词映射到项目行业分类 |
| `a` | 官方公告 | 腾讯表格“官方公告”链接 |
| `u` | 投递链接 | 投递链接或推文地址 |

去重键为：

```text
公司名称 + 岗位标题 + 地点
```

## 7. 腾讯文档同步命令

```bash
# 生成本地 jobs.json
python scripts/sync_tencent_docs.py

# 只打印统计，不写文件
python scripts/sync_tencent_docs.py --dry

# 生成数据，然后提交并推送到 origin/main
python scripts/sync_tencent_docs.py --push
```

`--push` 会直接执行：

```text
git add jobs.json
git commit
git push origin main
```

运行前应确认当前分支、数据量和工作区状态。

## 8. 二次开发时需要优先注意的问题

### 8.1 两个页面入口已经分叉

`index.html` 是唯一正式入口；旧版已归档到 `archive/xiaozhao-radar.html`。新增功能只维护正式入口，避免两套代码再次分叉。

### 8.2 `index.html` 是超大单文件

页面逻辑、样式和站点配置耦合在一起。修改某项功能容易影响其他区域，也不利于测试。后续可以按实际需求逐步拆为：

```text
index.html
assets/styles.css
src/app.js
src/crawlers.js
src/data-loader.js
data/crawl-sites.json
jobs.json
```

不要为了拆分而一次性重写整个项目，优先从最常改动的站点配置和数据加载逻辑开始。

### 8.3 同步失败可能覆盖完整数据

当前脚本某个子表拉取失败后仍可能把部分结果写入 `jobs.json`。发布前应增加：

- 两张表都成功的检查；
- 最小数据量检查；
- `count` 与数组长度检查；
- 临时文件写入后再原子替换；
- 与上一版本数据量差异过大时停止发布。

### 8.4 腾讯接口和通用网页解析都比较脆弱

- 腾讯文档依赖非公开接口；
- 企业网页没有逐站解析器，主要依赖 Markdown 和关键词；
- 动态渲染、登录、验证码、页面改版都可能导致空结果或误识别；
- 抓取结果不代表已经逐条验证岗位真实性和有效期。

### 8.5 数据存在多份副本

目前至少包括：

- `jobs.json`；
- `_jobs.json`；
- 浏览器 localStorage。

`jobs.json` 是正式发布数据，浏览器 localStorage 只保存用户缓存和个人跟进信息。

### 8.6 文档、版本和实际代码不完全一致

当前可见的不一致包括：

- README 的数据量和更新时间落后于 `jobs.json`；
- `index.html`、归档页面和 README 显示的历史版本不同；
- README 提到的 `clis/xiaozhao` 目录不存在；
- README 声称两个 HTML 同步，但实际功能差异很大。

做发布或结构调整时应一起校正文档和版本信息。

## 9. 推荐阅读顺序

首次接手项目建议按以下顺序阅读：

1. `docs/了解项目.md`：掌握整体结构和数据链路；
2. `docs/SYNC.md`：了解腾讯文档字段与发布流程；
3. `scripts/sync_tencent_docs.py`：理解离线数据生成；
4. `index.html` 中的 `loadRemoteJobs`：理解页面数据加载；
5. `index.html` 中的 `CRAWL_SITES` 和 Firecrawl/AnySearch 调用：理解按需抓取；
6. `tools/proxy.js`：理解本地网络转发边界；
7. 必要时查看 `archive/xiaozhao-radar.html` 了解旧版实现。

## 10. 合规与安全边界

- 只抓取有权访问和使用的公开数据；
- 遵守目标网站服务条款、robots 规则和访问频率限制；
- 不要在公开前端中长期保存私人 API Key；
- `tools/proxy.js` 能转发外部请求，不应直接暴露到公网；
- 对聚合数据应保留来源标识，并避免把未经验证的信息描述为企业官方确认结果。
